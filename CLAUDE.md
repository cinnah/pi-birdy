# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Birdy: a Raspberry Pi 4 + Camera Module v2.1 behind a window photographs birds at a feeder, filters non-bird motion with a local TFLite model, stores photos + metadata in SQLite, and serves a LAN-only review page.

The authoritative design is `docs/superpowers/specs/2026-10-03-capture-core-design.md` (sub-project 1), together with `docs/superpowers/specs/2026-10-03-settings-page-design.md` for the settings page and live reload (1b), `docs/superpowers/specs/2026-11-06-bioclip-species-design.md` for species ID (BioCLIP 2 and the local species list; it replaces the species model of `2026-10-03-species-recognition-design.md`), `docs/superpowers/specs/2026-11-06-detector-gate-design.md` for the detector half of the bird gate, `docs/superpowers/specs/2026-11-07-visits-and-corrections-design.md` for visits and species corrections (it supersedes Plan B of `2026-10-05-recognition-improvements-design.md`; its last section lists where the code differs), `docs/superpowers/specs/2026-11-24-dslr-camera-design.md` for the DSLR second camera, and `docs/superpowers/specs/2026-10-03-telegram-alerts-design.md` for Telegram alerts (6) and `docs/superpowers/specs/2026-10-04-publishing-design.md` for the public gallery (3). Read them before implementing anything; module interfaces, config keys, DB schema and defaults are all specified there. Sub-projects 4–5 (multi-site onboarding, e-ink) are out of scope unless asked.

## Architecture

One Python process, one systemd service, five threads (six with Telegram alerts enabled, seven with publishing enabled) talking through narrow interfaces:

```
capture ──MotionEvent──▶ pipeline (queue + worker) ──▶ classifier
   │                          │ model verdict
   │                          ▼
   │                        visits (group · vote · resolve · correct · 5 s tick)
   │                          │ final labels
   └──────────────────────────┴──▶ store (SQLite WAL + photos/thumbs on disk)
                                     ▲
web (FastAPI + /settings) ───────────┘      retention (hourly thread) ──▶ store, visits
   └── Fix panel ──▶ visits

config watcher (5 s stat of birdy.toml) ──▶ LiveConfig ◀── web POST /settings

telegram notifier (queue + worker) ◀── visits (one alert per visit, on the 5 s tick)

publisher (mirror + rsync) ◀── visits / web publish buttons
```

- `birdy/capture.py` is the **only** module that imports `picamera2`. Everything else must import and test on the Mac. Keep it that way; put any new camera-touching code there.
- `birdy/motion.py` is a pure-numpy/OpenCV detector (ROI mask → running background → diff → threshold → cooldown) so it can be tested with synthetic 320×240 frames. No camera code in it. It also returns the union box of the changed-pixel blobs (`MotionResult.bbox`); `crop_box()` turns a capture's stored box + the current ROI into the crop to classify: a square 2× the motion box (min 40 lores px, shifted inside the frame), or the ROI box + 10 % when there is no box or the motion covers > 50 % of the ROI box.
- `birdy/classifier.py` exposes a `Classifier` protocol returning `Prediction(is_bird, confidence, species, species_confidence, detector_confidence, detector_box, embedding)` (`embedding`: the BioCLIP image embedding when the species model ran, for the visit vote). The implementation is `TwoStageClassifier`: an ImageNet gate (`ImageNetBirdClassifier.predict` → P(bird), summed over ImageNet bird classes from MobileNetV2), a COCO object detector (`birdy/detector.py`, Coral EfficientDet-Lite0; `BirdDetector.best_bird` → the top `bird` detection with its box) and `BioClipSpecies` (`birdy/species.py`: BioCLIP 2 image tower as int8 ONNX run with onnxruntime, zero-shot — the image embedding is scored against text embeddings of the current candidate names from the bank `models/bioclip2-birds.npz` and softmaxed over those candidates only; ~3.5 s per photo on the Pi 4), all run on one decoded crop (`CropLoader`) under one lock. A photo is a bird when the gate ≥ `classifier.threshold` **or** the detector ≥ `detector.threshold`; `confidence` is the max of the two. **Species runs only when the photo is a bird** (measured 2026-11-06: BioCLIP gives 14 % of empty frames a confident name otherwise — a closed name list has no "nothing here" answer) and is reported when its top-1 probability ≥ `species.threshold`; a non-bird has no species and there is no rescue any more. A species-model failure degrades to "bird, no species", logged once per distinct error. The candidate set is the local species list + `species.include` − `species.exclude` (the whole bank when there is no list and nothing is configured); `_refresh_candidates` re-applies it inside the classifier lock, before the next species run, whenever the list's `version` or the `[species]` config changed. The detector box is stored (`det_confidence`, `det_x/y/w/h`, fractions of the classified crop; `det_confidence` NULL = never run, 0 = ran, nothing found) and drawn on the **Model view** crop; it is not used for the species crop (measured 2026-11-06: no gain). Measured the same day on 117 hand-labelled bird photos: gate alone kept 53, gate OR detector ≥ 0.2 keeps 104 (`docs/superpowers/specs/2026-11-06-detector-gate-design.md`); BioCLIP 2 names 99 of 117 Black Redstarts where the 2017 iNat model named 13 (`docs/superpowers/specs/2026-11-06-bioclip-species-design.md`).
- The pipeline worker and the web upload box share **one** `TwoStageClassifier` (built in `cmd_run`); TFLite and onnxruntime sessions are shared, serialised under one lock (TFLite interpreters aren't thread-safe; candidate updates happen under the same lock). Don't build a second one for the web.
- `birdy/dslr.py` is the **only** module that runs `gphoto2` (a Canon EOS 50D on USB, same window as the Pi camera). The `Dslr` is always built in `cmd_run` and `dslr.enabled` is a live switch (**Use the 50D** on `/settings`; nothing runs `gphoto2` while it is off, and switching it on there asks the camera once with `info()` so the page says ready / not connected). While it is on, the pipeline uses the classifier's staged API: `verdict` (gate + detector on the Pi crop) → for a bird whose Pi photo is ≤ 10 s old (`FRESH_SECONDS`; never the backlog or backfill) `Dslr.capture` (~1.2 s, one frame, `…_eos.jpg` beside the Pi photo) → `locate` (the detector on `dslr.region` of that frame) → `name` (BioCLIP) on a square around the bird in the DSLR frame (`species_crop`: 2× the box's longer side, ≥ 224 px), or on the Pi crop when no bird was found or the camera failed. `captures.path` always stays the Pi photo; `dslr_path` + `dslr_x/y/w/h` (the bird's box, fractions of the DSLR frame) record the frame, and `Capture.photo` — the DSLR frame when the box is set or `dslr_main` is (a photo taken by hand), else the Pi photo — is what the grid, lightbox, Model view, gallery mirror and Telegram use. The main photo never changes after first classification. A DSLR frame with no bird (and not `dslr_main`) is kept `retention.non_bird_days` (`store.purge_dslr_unused`), linked from the tile as **50D frame**; that link and **Pi photo** (class `aux`) open in the grid's lightbox like the photo itself. Failures (camera off, timeout, `dslr.daily_cap` reached — counted from the DB per local day) are one warning per distinct error and the capture carries on with the Pi photo. Everything is sequential on the pipeline thread: mid-visit shots can land 4–5 s late behind a BioCLIP run; the spec's *Later* section has the measurement that would justify a second thread.
- `birdy/species_list.py` — the site's local species list, which is the BioCLIP candidate set. It fetches iNaturalist `observations/species_counts` (birds, research grade, `species.region_radius_km` around `site.lat/lon`), keeps rank-species rows with ≥ 3 observations, and retries once at 4× the radius when fewer than 20 species come back; ≤ 1 request/s, 20-page cap. It is stored atomically at `data/species/local.json` (`fetched_at`, `lat`, `lon`, `radius_km`, `species: [{id, latin, common, count}]`; ids are iNat taxon ids, shared with the bank). `cmd_run` starts a one-shot `species-list` thread at service start that fetches when the file is missing, older than 90 days, or its lat/lon/configured radius differ from the config (`radius_km` is the radius actually used, 4× after a retry; `configured_radius_km` the configured one); `cmd_run` waits up to 60 s for the first species-list fetch when none is stored, so the history rename uses the local list, then applies the candidates (`apply_candidates`) before the pipeline starts; it never saves a list of fewer than 20 species, a failure is one warning and keeps the old file, and a saved list bumps `SpeciesList.version` so the classifier re-applies the candidates. `species.include`/`exclude` are live, matched casefold against the bank's latin or common names; unknown names are rejected by the settings page (with the name in the error) and, from an edited `birdy.toml`, warned once and ignored. No `site.lat/lon` = no list = the whole bank (11,385 species), and `/settings` says "set a location to enable it". `/settings` shows the list state (count, radius, age), `/species` the candidate count. `birdy species-list` prints the list (count, radius, age, every species by observation count, and any unknown include/exclude names), fetching it first when none is stored; `--refresh` fetches now (exit 1 if that fails, still printing the old list). The service picks up a CLI-fetched list only at its next start.
- `species_checked` and `detector_checked` mark rows the species model / the detector have seen. Each pipeline sweep backfills up to 50 older `done` rows with either flag unset (`_backfill`, `store.classification_backlog`): it never demotes a bird to non-bird (the merged verdict, old bird OR new bird, is what `store_verdict` writes to `model_is_bird`, so visit membership keeps it; and a known bird is always shown to the species model (`known_bird`), so a stricter gate can't strip its name), promotes a non-bird the detector finds (a promoted row gets a species like a new row), never flips a `done` row to `error` on failure (it marks it checked instead), yields as soon as a live event is queued, hands each row to `Visits.photo_classified(live=False)` (never alerts, may publish), ticks visits between rows, and logs one summary line per sweep (`backfill: N rows, N with species, N promoted, N renamed, N remaining`). The same sweep then resolves `done` rows that have a verdict but no final label (`store.unresolved_done`: a crash between `store_verdict` and `Visits`). Species: a row with `species_checked = 0` always takes the new verdict as its `model_species` and embedding, even "no species" (its old name came from another model); a row the species model has already seen keeps its model label and stored embedding (so publish slots and past rankings don't move when only the ROI changed). Either way the photo's final name comes from `Visits`: the visit's name wins over the photo's own unless the photo's own p ≥ 0.8. `store.reset_species_for_model(model_id)` (called in `cmd_run`; the id is kept in the `meta` table as `species_model`) sets `species_checked = 0` on every `done`, `is_bird = 1`, uncorrected (`manual_at IS NULL`) row when the species model id changes and logs the count, so a model swap renames history through the backfill (~40 min for 640 rows at 3.5 s each, 50 per 5-min sweep). A rename (old species set and different, including old → none) is handled in `Visits.resolve`: `published = 'auto'` is cleared (`forced`/`hidden` survive) and both the old and the new species/day are re-ranked, so the old slot moves to the next-best photo. After a deploy that adds a model, every stored row is re-gated within `rows / 50` sweeps (5 min each; ~1 h for 640 rows on the gate + detector; birds also cost a BioCLIP run).
- `birdy/store.py` owns the single write connection (locked, `check_same_thread=False`); capture, pipeline, visits, web and retention all write through it. The web thread reads through the same locked connection. The only other writer is the one-shot `birdy purge` CLI, which is safe under WAL.
- Nothing is dropped on overload: capture inserts the row as `status='pending'` before enqueueing, and the pipeline's 5-minute backlog sweep reclassifies anything still pending.
- Manual delete: every grid tile has a Delete button (`POST /captures/{id}/delete` → `store.delete_capture`: row first, then photo + thumb; works on birds too, 404 for an unknown id), and the non-birds view has a bulk "Delete these N" (`POST /captures/delete-non-birds` with the page's `ids`; `store.delete_non_birds` only deletes non-bird/error rows, so a bird id posted there is ignored). Both take the grid's `next` (only `/` or `/?…`), use a two-tap confirm in the page, and call `visits.photo_removed(visit_id)` (the visit is re-resolved, or deleted when empty) and `publisher.forget(capture)` so a deleted published photo's slot goes to the next-best photo and the gallery drops it on the next sync.
- **Visits and corrections** (`birdy/visits.py`). A `visits` table (`started_at`/`ended_at` UTC, `closed`, `species`, `species_confidence`, `alert` = `pending|sent|skipped`) plus `captures.visit_id` and `captures.embedding` (the photo's L2-normalised BioCLIP image embedding, 768 × float16; NULL until the species model has seen the photo). The pipeline stores the model's verdict only (`store.store_verdict` → `model_*`, `embedding`, `det_*`, the checked flags, `status`; `update_classification` still writes model + final columns and is kept for tests only) and hands the row to `Visits.photo_classified(capture, live)`, the only writer of the final `is_bird/confidence/species/species_confidence` that every reader uses (`write_final`; one `RLock`; no model runs in it — all arithmetic on stored embeddings). Membership = `manual_is_bird = 1 OR (manual_is_bird IS NULL AND model_is_bird = 1)` (`store._BIRD_MEMBER`), never the final column. A member with no visit joins the visit whose span ± `visits.gap_seconds` (default 60, 10–600, live, on `/settings`) holds its time, ignoring visits with no bird member; none → a new visit (`alert = 'pending'` live, `'skipped'` otherwise); several → merged into the lowest id (alert `sent` if any was, else `skipped` if any was, else `pending`). A non-member with no visit is resolved alone (`resolve_single`: final = correction, else model; a species only for a bird). `resolve(visit)` writes each photo's final label: correction > the photo's own top-1 when it differs from the vote and its own p ≥ `KEEP_OWN = 0.8` (a second bird in frame; so a visit whose members confidently disagree stays per-photo) > the vote (mean of the members' embeddings, renormalised, scored against the current candidates with `species.score_candidates`, reported at ≥ `species.threshold`; with no bank or no embeddings yet, the members' most common `model_species`) > bird, no species. A model non-bird inside a visit stays a non-bird; `species_confidence` is the photo's own p for its final name (a corrected name carries `model_confidence`, so corrected visits still rank). Publishing follows every label change: final columns first, then a renamed bird loses `auto` (`forced`/`hidden` kept), a photo whose final label is non-bird loses any publish state and the mirror syncs, and each touched (species, local day) — old and new names, plus same-name confidence changes — is re-ranked once through `Publisher.evaluate_day`. `tick()` runs on the pipeline thread every 5 s (`Pipeline(tick_interval=)`, also between backfill rows): a visit with no photo for `gap_seconds` is resolved and closed, and a `pending` visit alerts once — at close, or after `ALERT_AFTER = 300` s open with the vote so far — unless its last photo is > 10 min old at that moment (`LATE`: restart, backlog) or it has no species (both → `skipped`, logged). The alert photo is the visit's highest-`species_confidence` photo of its species (ties: lower id); `first_seen` = `store.count_visits_with_species(species) == 1` (counting only visits that still have a bird member). Corrections: a **Fix** panel on every `done` tile (a species field with a `<datalist>` of the local list by observation count + species seen, **Set**, **Not a bird** on birds, **Bird, species unknown**, **Back to model** when corrected) posts `POST /captures/{id}/label` with `label=not_bird|bird_unknown|species|clear` (`species` takes `species_name`: any bank latin or common name, case-insensitive, stored as the bank's common name; `label=species:<name>` also works) and the grid's `next` rule; 400 another label or an empty/unknown name, 404 unknown id, 409 unless `status = 'done'`, 503 for `species`/`bird_unknown` when no `Visits` is wired (`not_bird`/`clear` then fall back to the per-photo `store.mark_not_bird`/`clear_correction`). `Visits.correct` applies the correction to the whole visit (`set_manual_visit`; a bird correction on a photo with no visit `assign`s it first, alert `skipped`); joined or merged visits take the most recent correction; `clear` restores the model verdict and detaches the photos that are then non-members (each resolved alone); on a photo with no visit whose model verdict is bird, `clear` `assign`s it like a freshly classified photo (alert `skipped`; `store.queue_embedding` puts it back in the species backlog when it has no embedding). No two-tap confirm (corrections are reversible) and a correction never alerts. The grid takes `?visit=N` (that visit's photos, forces `filter=all`); tiles show `visit · N` (N > 1, linking there), a `you` stamp when corrected and, muted, the model's verdict `model: <model_species> <p>`. Corrected rows (`manual_at`) are never in the species backlog and never purged (kept as labelled examples).
- Retention deletes `is_bird = 0` and `status = 'error'` rows older than `retention.non_bird_days`; rows with any `published` state or a correction (`manual_at`) are kept, and bird photos are never auto-deleted. `store.purge_non_birds` returns `(count, visit ids)`; the service's `RetentionJob` passes each id to `visits.photo_removed` (re-resolve, delete when empty). The one-shot `birdy purge` runs without `Visits` (no classifier is built): a visit it leaves without a bird is never revisited, but `count_visits_with_species` no longer counts it.
- `birdy/web/app.py` serves the capture grid, `/status`, `/frame.jpg`, `/roi.png` (ROI overlay; still served, `birdy roi` points to it while the service holds the camera) the `/settings` page (plus `POST /settings/test-alert`, which sends a Telegram message and writes nothing), `/species` (per-species summary + an upload box that `POST /classify`s a photo and shows the verdict, the detector score and the top-3 species, or "species: skipped (not a bird)"; it runs on the full uploaded image with no ROI crop and nothing is stored), a species dropdown filter on `/` (returns birds only: `is_bird = 1`), and `last_species` in `/status`. `POST /settings` writes `birdy.toml` (never the DB). When publishing is enabled the grid also gets publish badges, Publish/Hide/Auto buttons (`POST /captures/{id}/publish` with `state=forced|hidden|auto` → `publisher.set_manual`; 404 unknown id, 503 when publishing is disabled; 303 to the form's `next`, accepted only if it is `/` or starts with `/?`, else `/`) and a `filter=published` option.
- Web UI look: all pages extend `templates/_base.html` (OSD strip; the one `/status` poll, re-broadcast as a `birdy:status` event) and share `web/static/osd.css` plus the self-hosted Martian Mono font (no remote assets). Visual rules live in `DESIGN.md`, product context in `PRODUCT.md`. The grid at `/` defaults to `filter=birds`.
- `birdy/live.py` — `LiveConfig` holds the current `Config` + a version. Tunables (`motion.*`, `classifier.threshold`, `detector.threshold`, `species.threshold/include/exclude`, `telegram.watchlist/alert_new_species/cooldown_minutes`, `visits.gap_seconds`, site/daylight, retention) are read through `live.get()` on use; `telegram.enabled` is also checked per alert, so `enabled = false` silences alerts live but `enabled = true` needs a restart (the notifier isn't built otherwise); the capture loop rebuilds its motion detector/daylight gate when `live.version` changes (and `motion`, `site.lat/lon` or `daylight` differ). Camera/web/storage/model keys (`classifier.*` except `threshold`, `species.model/bank/region_radius_km`, `detector.model/labels`) and `telegram.enabled/bot_token/chat_id/base_url` are read once at startup — changing them needs a restart (the watcher logs a warning).
- Camera switch: `POST /camera` (`mode=on|off|auto`, `next` = `/`, `/?…` or `/settings`) sets `RuntimeState.set_override`, shown in the grid header and at the top of `/settings`. On/off holds until the next daylight change at the time it was pressed (`DaylightGate.next_change`; with no lat/lon, until switched back), then the schedule resumes; `auto` returns to the schedule now. The capture loop asks `state.camera_wanted(gate, now)` and wakes within ~1 s on a change (`override_version`). It's in memory only: a restart drops it. State `manual_off` = switched off by hand. **Take a photo** (`POST /camera/capture`, same `next` rule) sets `RuntimeState.request_capture()`; the capture loop consumes it on its next frame (~0.1 s) and stores a still with no motion box (so the classifier uses the ROI crop) and the current motion score, then the pipeline classifies it as usual. The button shows only while `state = 'capturing'`; the route is 409 otherwise, and a request pending from before a camera session is discarded at session start. Since the grid defaults to `filter=birds`, a manual shot the model calls non-bird appears under *not birds*. A manual shot carries `MotionEvent.manual = True`, so with the extra camera on it fires the DSLR whatever the verdict, and that frame is the capture's main photo even with no bird in it (`captures.dslr_main = 1`; the tile links the Pi photo as **Pi photo**).
- `birdy/settings.py` + `birdy/watcher.py` — the `/settings` page validates and atomically rewrites `birdy.toml` (comments are lost; `birdy.toml.example` keeps the docs) and applies it live; `ConfigWatcher` reloads the file when it's edited over SSH (invalid edits are logged and ignored until restart).
- `birdy/notify.py` — `AlertPolicy` is pure: watchlist names must be iNaturalist English common names as BioCLIP reports them (e.g. "Common Hoopoe", "Eurasian Blue Tit"; the settings page rejects names that aren't a stored species name, i.e. the bank's common name or the latin one when there is none: `SpeciesList.unknown_names(..., reported_only=True)` against `Bank.reported_names`), the match is case-insensitive, a first-ever species gives reason `"new"` (bypasses the cooldown), otherwise a per-species cooldown held in memory. `TelegramNotifier` has a bounded queue (20; newest dropped with a warning when full) and one worker thread that `sendPhoto`s the full-res JPEG, retries after 5/15/45 s (not on 400/401/403, which can't succeed) then logs once and drops, and falls back to a text message if the photo was purged. It is fed only by `Visits.tick`, once per visit, with the visit's best photo: `consider(capture_id, photo_path, species, species_confidence, captured_at, first_seen)` → the reason when queued (visit `alert = 'sent'`), else None (`skipped`); backfill and migrated visits are `skipped` and never reach it, and a `consider()` failure is logged and the visit marked `skipped`. "First-ever" (`first_seen`) means the first *visit* with that species at alert time, so a species the backfill already put on an older visit never gets a "new" alert. Queued alerts are dropped on shutdown. The web shares the same instance for `POST /settings/test-alert` (`send_test()`, synchronous; 502 with Telegram's description on error, 503 when alerts are disabled). When `telegram.enabled = false` the notifier isn't constructed at all.
- `birdy/publish.py` — `rank_day` is pure: per species and local day, `forced`/`hidden` win (forced doesn't use a slot), then the best `publish.per_species_per_day` photos at or above `publish.min_confidence` (ties: lower id) get `auto`. `Publisher.evaluate_day(species, when)` re-ranks that species/day whenever `Visits` changes a label (live **and** backfill — historical photos may be published, unlike alerts; `evaluate(capture)` and `forget(capture)` wrap it); `set_manual(id, 'forced'|'hidden'|None)` is the review page's Publish/Hide/Auto. The first time publishing is enabled (no `data/publish/` yet) the publisher ranks all history; `birdy publish --rerank` redoes that with the current thresholds. Its thread keeps `data/publish/` in sync with the DB — web copies ≤ 1600 px (JPEG 85, OpenCV `INTER_AREA`, never upscaled) written through a temp name, fsynced, then `os.replace` (a 0-byte mirror file — what a power cut left before the fsync — counts as missing and is remade), thumbs copied as is, `manifest.json` written atomically (per-pid temp) — then runs `rsync -az --delete --delete-after --delay-updates` (excluding `.lock` and `*.tmp*`; `--timeout=120` and `ConnectTimeout=20` bound stalls, a 1800 s wall-clock cap bounds the whole run — 3600 s for the `birdy publish` one-shot) to `user@host:remote_dir`: debounced 2 min after a change, at least every 15 min, first run right after start (reconcile). `stop()` interrupts a mirror build between photos; that run then pushes nothing and returns False. An unreadable original (0-byte, deleted) is set `hidden` and its day re-ranked so the next-best photo takes the slot; a mirror write failure (disk full) is retried next run and never hides. A run logs at info only when the published set changed (debug otherwise); an rsync failure is one warning per run. The gallery pages in `gallery/` (vanilla JS) render in the browser from `sites.json` + each site's manifest; nothing runs on the server. They are designed as a printed recording sheet (home = the daily record, species × feeders, `?day=YYYY-MM-DD` for a past sheet with ←/→ links to the previous/next day that has entries; `site.html` = a feeder's monthly sheet, species × days, from `stats.species[].days`; `species.html` = a species card); fonts are self-hosted in `gallery/fonts/` (Libre Franklin, Courier Prime, OFL), and the look is recorded in `gallery/DESIGN.md`, not the Pi UI's `DESIGN.md`. `gallery/about.html` is the one static page (no JS): manifesto, how it works, the rig, how to join, code, credits; its copy lives in the HTML itself, and the rig photo slot is `gallery/about/rig.jpg` (a ruled `.plate` placeholder stands in the `figure` until the photo is supplied; then replace the `div.plate` with `<img src="about/rig.jpg" srcset="about/rig-thumb.jpg 400w, about/rig.jpg 1600w" sizes="(max-width: 719px) calc(100vw - 32px), 560px" alt="…">`).
- A settings-page save writes the running config: it overwrites SSH edits made in the last few seconds that the watcher hasn't applied yet, and drops comments and unknown keys.

## Conventions and gotchas

- Config is `birdy.toml` (gitignored). Every key must be documented in `birdy.toml.example`; add new keys to both the dataclass in `config.py` and the example file.
- ROI polygon coordinates are in **lores** (320×240) space. The classifier scales that bbox to main-stream coordinates before cropping. Each capture's motion box is stored as `motion_x/y/w/h`, fractions of the lores frame (NULL for captures from before the motion crop, which keep the ROI crop). `camera.main_size` and `lores_size` must share an aspect ratio (validated).
- `picamera2` and OpenCV come from apt on the Pi, so the Pi venv is created with `--system-site-packages`. Do not add them as pip dependencies in `pyproject.toml`.
- The Pi runs Raspberry Pi OS Trixie (Debian 13, Python 3.13, NumPy 2.x, OpenCV 4.10 from apt). Never pin `numpy` in `pyproject.toml`: with `--system-site-packages` the apt NumPy must satisfy it, or pip installs a second NumPy that breaks the apt `cv2`. `opencv-python-headless` is a dev-only extra for the Mac.
- Photos live at `data/photos/YYYY/MM/DD/HHMMSS_mmm.jpg` with thumbs mirrored under `data/thumbs/`; paths in the DB are relative to those roots. `data/`, `.venv/` and `birdy.toml` are excluded from deploy rsync.
- `captured_at` is stored as **UTC** ISO 8601 (so string `<` comparisons are chronological) and converted to local time in the template. Photo *paths* use local time.
- The ImageNet gate and the COCO detector in `models/` are committed with their license and labels; `imagenet_bird_classes.txt` is the source of truth for which class indices count as "bird". The BioCLIP 2 ONNX (`bioclip2-vision-int8.onnx`, ~292 MB) and the name bank (`bioclip2-birds.npz`, ~20 MB) are **gitignored** (GitHub's size limit) and built on the Mac by `deploy/build-species-model.sh` (its scratch venv `.build-venv/` is gitignored too); `deploy/deploy.sh` rsyncs `models/`, so the first deploy after a build pushes them. `deploy/deploy.sh` refuses to run when the BioCLIP files are missing (its `rsync --delete` would remove them from the Pi), so build them before deploying from a fresh clone or worktree; it never ships the build's `bioclip2-vision-fp32.onnx`. Rebuild both together: the bank records `bioclip-2/int8/<first 12 hex of the ONNX's sha256>` and the service refuses a mismatched pair (model error, exit 2). Tests never need them (real-model tests skip when absent).
- The hosted MobileNetV2 TFLite model outputs **logits** (no softmax layer); `ImageNetBirdClassifier` applies softmax itself. Don't "fix" the dequantized sum ≠ 1.
- All three models must get the **same RGB** array (`CropLoader` converts once): the gate, the detector and BioCLIP. Feeding BGR silently degrades results — a blue tit comes out as a hummingbird.
- `species.model/bank/region_radius_km` are restart-only (the watcher warns; a radius change refetches the list at the next start); `species.threshold/include/exclude` are live and on `/settings`. The Pi's old `species.rescue_threshold` key (and `species.labels`) is ignored by `load_config` and dropped by the next settings-page save; an old `species.model = …tflite` path is replaced by the default with a warning.
- `onnxruntime` is a pip dependency in `pyproject.toml` (aarch64 cp313 wheels exist; no apt package needed); `onnx` is a dev-only extra (the tests build a stand-in ONNX).
- `birdy classify <file>` prints the final verdict with the raw gate and detector probabilities, then the gate's top-5, the detector's verdict (`detector (COCO): bird 0.773 box …` or `no bird (best: potted plant 0.55)`), then `species (BioCLIP 2, N candidates):` with the top-5, or `species: skipped (not a bird)` — the first thing to run when a capture looks misclassified. `birdy classify --capture <id>` classifies a stored capture with the crop the service uses and prints which crop (`motion`/`roi`, or `dslr` for a capture promoted to its 50D frame); the grid's **Model view** link (`/captures/{id}/crop.jpg`) shows the same crop.
- `MotionDetector` suppresses triggers for its first `warmup_frames` (default 10) so camera auto-exposure settling at session start doesn't produce junk captures.
- `telegram.bot_token` is a secret. It lives only in the Pi's `birdy.toml` (0600, gitignored, rsync-excluded), is written back by every settings-page save (`config_to_dict` includes it, so a save never wipes it), is excluded from `repr(Config)` (`field(repr=False)`), is never logged, and every `TelegramError` message is redacted (`_redact`; request URLs are never included). Never put it in git, docs, tests, memory or log lines. The settings page shows only "set"/"not set".
- `telegram.enabled`, `bot_token`, `chat_id`, `base_url` are restart-only (the watcher warns); `watchlist`, `alert_new_species`, `cooldown_minutes` are live. Cooldown state is in memory, so a restart may re-alert a species once; "new species" is derived from the DB (`store.count_visits_with_species(species) == 1`, the first visit) and survives restarts.
- Telegram rejects photos over 10 MB or with width + height over 10,000: `notify._telegram_jpeg` sends a 2560 px copy for a file over 8 MB or past that size.
- Visits migration: `store.migrate_visits(gap_seconds)` runs once from `cmd_run` (not on `Store` open; before the pipeline starts), guarded by `meta.visits_version = '1'` (re-checked inside the transaction). It backs the DB up to `data/birdy.db.bak-visits` first, then in one `BEGIN IMMEDIATE` transaction copies the final columns into `model_*` on uncorrected `done` rows, groups the bird members over all history (a gap > `gap_seconds` starts a new visit; all `closed = 1`, `alert = 'skipped'`, species = the members' most common name) and sets `species_checked = 0` on every uncorrected bird without an embedding, so the backfill computes the embeddings (~3.5 s per bird, 50 per 5-min sweep: 141 birds ≈ 15–20 min; `cmd_run` logs the count and an ETA). When publishing is on, `publisher.evaluate_all()` re-ranks every day once after `pipeline.start()`. Expect renames inside visits in the first sweeps (`backfill: … N renamed`) as the embedding vote replaces per-photo names; history never alerts. Rollback: `sudo systemctl stop birdy`, delete `data/birdy.db-wal` and `data/birdy.db-shm`, copy `data/birdy.db.bak-visits` over `data/birdy.db`, and deploy the pre-visits code (with the visits code the next start migrates again).
- `detector.model/labels` are restart-only (the watcher warns); `detector.threshold` is live and on `/settings`. Default 0.2 was measured on 2026-11-06. Person-in-frame false positives are rare and handled with **Not a bird**. `models/coco_labels.txt` is one name per line, line index = class id, `n/a` for unused COCO ids — never filter those lines.
- **Take a test frame** on `/settings` (`POST /settings/dslr-frame`, works with the switch off, subject to the daily cap check, 303 on success so a refresh can't fire the shutter again, 502 with gphoto2's message, 503 with no `Dslr`) fires the extra camera once into `data/dslr-test.jpg` (the same file `birdy dslr shot` writes); `GET /settings/dslr-frame.jpg` serves a ≤ 1280 px copy (`data/dslr-test-web.jpg`, remade when the frame is newer) and the page lets you drag a box on it to fill `dslr.region`; a click that draws nothing opens the full-size file (`?full=1`) in a lightbox.
- Auto shutter (`dslr.auto_shutter`, live, a switch on `/settings`, off by default; the DSLR must be in **Tv**): `capture._capture_still` reads `Lux` from the Pi still's metadata (`picam2.capture_file` returns it) into `MotionEvent.lux`; before a DSLR shot the pipeline picks the fastest speed of `dslr.SHUTTER_LADDER` (1/500 … 1/60) whose time ≥ `k / lux` (`pick_shutter`) and passes it to `Dslr.capture(dest, shutter)`, which sets `shutterspeed` in the same `gphoto2` call. `k` (lux × seconds, default `EXPOSURE_K_DEFAULT = 1.5`, a guess) is kept in the `meta` table as `dslr_exposure_k` and corrected after every such frame from the mean grey level of `dslr.region` (`adapt_exposure_k`: darker than 75 % of `TARGET_BRIGHTNESS = 100` → k grows by the shortfall, ≤ 4× per frame, not at 1/60; otherwise k shrinks 5 %, not at 1/500), logged as `capture N: 50D at 1/250 for 320 lux, brightness 96 (k 1.50 -> 1.43)`. No light reading, or the switch off, leaves the camera's own speed. **Take a test frame** and `birdy dslr shot` never set the speed. Measured 2026-11-24 17:00 (sunset, f/4, ISO 1600): 1/500 → brightness 12, 1/250 → 25, 1/125 → 49.
- `dslr.enabled`, `dslr.region` and `dslr.daily_cap` are all live and on `/settings` (section **Extra camera**); `/status` reports `dslr.state = "off"` while the switch is off. The 50D's exposure, ISO, image size and focus are set on the camera body, never by birdy; it must be on AC power with auto power off **Off**, lens on **MF**, `capturetarget = Internal RAM` (`birdy dslr info` warns otherwise). `gphoto2` comes from apt (`install.sh`). Tests never need it: `Dslr` takes a `runner` in place of `subprocess.run`.
- `publish.enabled/host/user/remote_dir/site_id/ssh_key` are restart-only; `min_confidence`/`per_species_per_day` are live but only affect days ranked from then on; `birdy publish --rerank` re-ranks history with the current thresholds, and that runs automatically the first time publishing is enabled. `published` states: `NULL`, `auto`, `forced`, `hidden`; the published set is `auto`+`forced`. `web_path` is the mirror copy's relative path (same as `path`). The manifest's `captured_at` is local time with offset and `site.utc_offset_minutes` lets the page compute the site's "today". `stats.species[].days` (`{local day: visits}` inside the 30-day window) feeds the monthly sheet; the pages fall back to counting published photos when a manifest (an older Pi) lacks it, and say so in the sheet's corner label.
- `FILTERS["published"]` exists; the nav shows it only when a publisher is configured.
- `remote_dir = "/"` is only safe with the rrsync-restricted key. With an unrestricted key, `rsync --delete` to `/` would be destructive — use the full path (`/srv/birdy/sites/<site_id>`).
- The publisher's ssh uses `StrictHostKeyChecking=accept-new`: if the server is re-keyed, every push fails with exit 255 until the Pi's `known_hosts` entry is removed (`ssh-keygen -R <host>` as the service user).
- `Publisher.stop()` doesn't flush: evaluations made right before shutdown are pushed by the reconcile run at the next start.
- Chrome on the Mac cannot open `birdy.local` because avahi advertises an IPv6 link-local address first; set `use-ipv6=no` in `/etc/avahi/avahi-daemon.conf` on the Pi and restart avahi (`sudo systemctl restart avahi-daemon`). The Pi's IP works meanwhile.
- The Mac shell losing the LAN mid-session (`No route to host` to every LAN host but the router, internet fine) is the macOS Local Network permission of the app hosting the session (VS Code), not the Pi.
- Adding a tunable key: `config.py` dataclass + validation, `birdy.toml.example`, `settings.py` (`SettingsPatch`, `config_to_dict`, `apply_patch`, `FIELD_KEYS`, `parse_settings_form`), `settings.html` form row, and the consumer must read it via `live.get()`. List-valued keys (`telegram.watchlist`, `species.include/exclude`) use `_str_list` in `config.py`, a textarea (one name per line) in `settings.html` and `_lines` in `parse_settings_form`. `test_config_to_dict_covers_every_field` fails if `config_to_dict` is forgotten.
